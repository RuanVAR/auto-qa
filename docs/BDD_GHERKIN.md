# BDD / Gherkin Support

> **Status:** Planned (Phase 9)
> **Depends on:** Phase 2 (Core Features), Phase 5.5 (RAG / AI Generation)

---

## Overview

BDD (Behavior-Driven Development) support adds native Given/When/Then syntax for writing and executing test cases. Tests can be authored in Gherkin, imported from `.feature` files, or generated by AI from requirements. At execution time, Gherkin steps are mapped to the platform's existing step types (CLICK, FILL, ASSERT_TEXT, etc.) via step definition bindings.

This gives teams two authoring modes:
1. **Structured steps** (existing) — explicit step types with selectors and values
2. **BDD/Gherkin** (new) — natural language Given/When/Then with step definition bindings

Both modes execute on the same runner infrastructure. BDD is an **authoring overlay**, not a separate engine.

## Architecture

```
┌─────────────────────────────────┐
│         Gherkin Editor          │
│  Given I am on the login page   │
│  When I enter "admin" / "pass"  │
│  Then I should see the dashboard│
└─────────────┬───────────────────┘
              │ parse
              ▼
┌─────────────────────────────────┐
│       Gherkin Parser            │
│  (cucumber-gherkin-utils)       │
│                                 │
│  Feature → Scenarios → Steps    │
└─────────────┬───────────────────┘
              │ bind
              ▼
┌─────────────────────────────────┐
│     Step Definition Registry    │
│                                 │
│  /^I am on the (.+) page$/     │
│  → NAVIGATE { url: $1 }        │
│                                 │
│  /^I enter "(.+)" (?:in|into)  │
│    (?:the )?(.+)$/             │
│  → FILL { selector: $2, val:$1}│
│                                 │
│  /^I should see "(.+)"$/      │
│  → ASSERT_TEXT { text: $1 }    │
└─────────────┬───────────────────┘
              │ resolve
              ▼
┌─────────────────────────────────┐
│    Native Step Definitions      │
│                                 │
│  NAVIGATE, CLICK, FILL,        │
│  ASSERT_TEXT, ASSERT_VISIBLE,   │
│  etc. (existing step runner)    │
└─────────────────────────────────┘
```

## Gherkin Language Support

### Supported Keywords

```gherkin
Feature: User Authentication
  As a user
  I want to log in to the platform
  So that I can access my dashboard

  Background:
    Given I am on the login page

  Scenario: Successful login
    When I enter "admin@example.com" in the email field
    And I enter "password123" in the password field
    And I click the "Sign In" button
    Then I should see the dashboard
    And the page title should contain "Dashboard"

  Scenario Outline: Login validation
    When I enter "<email>" in the email field
    And I enter "<password>" in the password field
    And I click the "Sign In" button
    Then I should see "<message>"

    Examples:
      | email              | password  | message              |
      |                    | pass123   | Email is required    |
      | bad@email.com      | wrong     | Invalid credentials  |
      | admin@example.com  |           | Password is required |

  @smoke @P0
  Scenario: Password reset link
    When I click the "Forgot password?" link
    Then I should be on the password reset page
```

### Supported Gherkin Elements

| Element | Description |
|---------|-------------|
| `Feature` | Top-level grouping (maps to our Feature) |
| `Scenario` | Individual test case (maps to TestDefinition) |
| `Scenario Outline` + `Examples` | Parameterized test (generates one TestDefinition per row) |
| `Background` | Steps shared across all scenarios in a feature |
| `Given` / `When` / `Then` / `And` / `But` | Step keywords |
| `@tag` | Tags for filtering and metadata (maps to test labels) |
| `#` | Comments |
| `"""` | Doc strings (multiline text) |
| `|` | Data tables |

## Step Definition Registry

### Built-in Step Definitions

The platform ships with a library of common step definitions that map Gherkin to native steps:

#### Navigation

```typescript
Given('I am on the {word} page', (page) => ({
  type: 'NAVIGATE',
  config: { url: `{{BASE_URL}}/${pageRoutes[page]}` }
}));

Given('I navigate to {string}', (url) => ({
  type: 'NAVIGATE',
  config: { url }
}));

When('I go back', () => ({
  type: 'NAVIGATE',
  config: { url: 'javascript:history.back()' }
}));
```

#### Interaction

```typescript
When('I click (on )(the ){string}( button/link/tab)', (label) => ({
  type: 'CLICK',
  description: `Click element labeled "${label}"`,
  config: { selector: `[aria-label="${label}"], button:has-text("${label}"), a:has-text("${label}")` }
}));

When('I enter/type {string} in(to) (the ){string}( field/input)', (value, field) => ({
  type: 'FILL',
  description: `Type "${value}" into ${field}`,
  config: { selector: `[aria-label="${field}"], [placeholder="${field}"], label:has-text("${field}") + input` }
}));

When('I select {string} from (the ){string}( dropdown/select)', (value, field) => ({
  type: 'SELECT',
  config: { selector: `[aria-label="${field}"]`, value }
}));

When('I check (the ){string}( checkbox)', (label) => ({
  type: 'CLICK',
  config: { selector: `label:has-text("${label}") input[type="checkbox"]` }
}));

When('I scroll (down/up)', (direction) => ({
  type: 'SCROLL',
  config: { direction: direction || 'down' }
}));

When('I hover over (the ){string}', (element) => ({
  type: 'HOVER',
  config: { selector: `[aria-label="${element}"], :has-text("${element}")` }
}));

When('I press (the ){word}( key)', (key) => ({
  type: 'PRESS_KEY',
  config: { key }
}));

When('I wait {int} second(s)', (seconds) => ({
  type: 'WAIT',
  config: { duration: seconds * 1000 }
}));
```

#### Assertions

```typescript
Then('I should see {string}', (text) => ({
  type: 'ASSERT_TEXT',
  config: { text }
}));

Then('I should not see {string}', (text) => ({
  type: 'ASSERT_TEXT',
  config: { text, negate: true }
}));

Then('the {string}( element) should be visible', (element) => ({
  type: 'ASSERT_VISIBLE',
  config: { selector: `[aria-label="${element}"], :has-text("${element}")` }
}));

Then('the page title should contain {string}', (text) => ({
  type: 'ASSERT_TEXT',
  config: { selector: 'title', text }
}));

Then('the URL should contain {string}', (path) => ({
  type: 'ASSERT_URL',
  config: { pattern: path }
}));

Then('I should be on the {word} page', (page) => ({
  type: 'ASSERT_URL',
  config: { pattern: pageRoutes[page] }
}));

Then('the {string}( field/input) should contain {string}', (field, value) => ({
  type: 'ASSERT_TEXT',
  config: { selector: `[aria-label="${field}"]`, text: value }
}));

Then('I should see {int} {string}( items/rows/cards/elements)', (count, element) => ({
  type: 'ASSERT_ELEMENT',
  config: { selector: `[data-testid="${element}"]`, count }
}));
```

#### Screenshots

```typescript
Then('I take a screenshot', () => ({
  type: 'SCREENSHOT'
}));

Then('I take a screenshot named {string}', (name) => ({
  type: 'SCREENSHOT',
  config: { name }
}));
```

### Custom Step Definitions

Projects can define their own step definitions that map to platform-specific actions:

```typescript
// Project-level step definition
{
  pattern: 'I log in as {string}',
  steps: [
    { type: 'NAVIGATE', config: { url: '{{BASE_URL}}/login' } },
    { type: 'FILL', config: { selector: '#email', value: '{{USERS.$1.email}}' } },
    { type: 'FILL', config: { selector: '#password', value: '{{USERS.$1.password}}' } },
    { type: 'CLICK', config: { selector: 'button[type="submit"]' } },
    { type: 'WAIT', config: { duration: 1000 } },
    { type: 'ASSERT_URL', config: { pattern: '/dashboard' } }
  ]
}
```

### AI Step Binding

When a Gherkin step doesn't match any registered definition, the AI can:

1. Attempt to resolve it using codebase context (RAG)
2. Generate a step definition binding
3. Flag it for human review if confidence is low

```
Given step: "I should see the order confirmation with total $49.99"

AI analysis:
  - No built-in match
  - RAG finds: OrderConfirmation component with `data-testid="order-total"`
  - Generated binding: ASSERT_TEXT { selector: '[data-testid="order-total"]', text: '$49.99' }
  - Confidence: 0.85
  - Status: auto-applied (above 0.7 threshold)
```

## Data Model

### TestDefinition Changes

```prisma
model TestDefinition {
  // ... existing fields ...

  // BDD fields (new)
  authoring     TestAuthoringMode @default(STRUCTURED)
  gherkinSource String?           // raw Gherkin text (Feature/Scenario block)
  gherkinParsed Json?             // parsed AST from Gherkin parser
  tags          String[]          // from @tag annotations

  // ... existing relations ...
}

enum TestAuthoringMode {
  STRUCTURED   // existing step-by-step
  BDD          // Gherkin Given/When/Then
}
```

### StepDefinitionBinding

```prisma
model StepDefinitionBinding {
  id          String   @id @default(uuid())
  projectId   String
  pattern     String   // Cucumber expression or regex
  description String?
  steps       Json     // array of native step configs
  isBuiltIn   Boolean  @default(false)
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  project     Project  @relation(fields: [projectId], references: [id])

  @@unique([projectId, pattern])
  @@index([projectId])
}
```

## Import / Export

### Feature File Import

Import standard `.feature` files:

```
POST /features/:id/import-gherkin
Content-Type: multipart/form-data

file: login.feature
```

**Import behavior:**
- Each `Scenario` becomes a `TestDefinition` with `authoring: BDD`
- `Scenario Outline` with N example rows becomes N `TestDefinition` records
- `Background` steps are prepended to each scenario
- `@tags` are stored in the `tags` array field
- Steps are matched against the step definition registry
- Unmatched steps are flagged with `NEEDS_BINDING` status

### Feature File Export (Cucumber-compatible)

```
GET /features/:id/export-gherkin
Accept: text/plain

→ Returns standard .feature file content
```

**Export behavior:**
- BDD tests export their raw `gherkinSource`
- Structured tests are reverse-mapped to Gherkin using step definitions
- Feature name + description from the Feature model
- Tags from test `tags` field
- Output is valid Gherkin parseable by Cucumber

### Bulk Import

```
POST /projects/:id/import-gherkin-bulk
Content-Type: multipart/form-data

files: [login.feature, checkout.feature, settings.feature]
targetModuleId: optional — create features in this module
```

## AI BDD Generation

### Generate Gherkin from Requirements

```
POST /features/:id/generate-bdd
{
  "description": "User should be able to reset their password via email",
  "repoIds": ["repo-uuid"],
  "style": "verbose"  // or "concise"
}
```

AI generates complete Gherkin scenarios using codebase context:

```gherkin
Feature: Password Reset
  As a user who forgot their password
  I want to reset it via email
  So that I can regain access to my account

  @smoke @auth
  Scenario: Request password reset
    Given I am on the login page
    When I click the "Forgot password?" link
    Then I should be on the password reset page
    When I enter "user@example.com" in the email field
    And I click the "Send Reset Link" button
    Then I should see "Reset link sent to your email"

  @auth @negative
  Scenario: Reset with invalid email
    Given I am on the password reset page
    When I enter "not-an-email" in the email field
    And I click the "Send Reset Link" button
    Then I should see "Please enter a valid email"
```

### Convert Structured to BDD

Existing structured tests can be converted to BDD format:

```
POST /tests/:id/convert-to-bdd
```

AI reads the existing steps and generates equivalent Gherkin, preserving all assertions and logic.

### Convert BDD to Structured

```
POST /tests/:id/convert-to-structured
```

Resolves all Gherkin steps through the step definition registry and produces native step definitions.

## Execution Flow

When a BDD test is executed:

1. **Parse** Gherkin source into AST (scenarios, steps)
2. **Resolve** each Gherkin step through the step definition registry
3. **Expand** composite step definitions into native step sequences
4. **Substitute** Scenario Outline parameters from Examples table
5. **Execute** native steps on the existing step runner (Playwright/API/Shell)
6. **Report** results at both the Gherkin step level and native step level

The run detail view shows both levels:
- **BDD view** — Given/When/Then steps with pass/fail
- **Detailed view** — expanded native steps with screenshots and timing
