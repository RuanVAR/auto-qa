# Extended Integrations

> **Status:** Planned (Phase 10)
> **Depends on:** Phase 5.3 (Notifications & Integrations), Phase 5.5 (GitHub/GitLab Repo Connections)

---

## Overview

Extends the Phase 5.8 plugin registry with additional first-class integrations. All integrations are registry-native plugins (manifest + capability contract), reusing the same install/binding/enablement model defined in `docs/PLUGIN_REGISTRY.md`.

**Existing integrations (Phase 5.3):** Email, Slack, Microsoft Teams, Jira, Custom Webhook

**New integrations (Phase 10):**

| Plugin | Primary Use | Transport |
|--------|-------------|-----------|
| Discord | Notifications | Incoming Webhook |
| GitHub Issues | Bug tracking | REST API (PAT / OAuth) |
| GitLab Issues | Bug tracking | REST API (PAT / OAuth) |
| Linear | Bug tracking | GraphQL API |
| Google Chat | Notifications | Incoming Webhook |
| ClickUp | Bug tracking + PM | REST API |
| PagerDuty | On-call alerts | Events API v2 |

## Discord Plugin

### When to use
Teams using Discord for engineering communication. Especially common in open-source projects and startups.

### Message Format

Discord Embed:
- **Color:** Red (`#ed4245`) on failure, Green (`#57f287`) on pass
- **Title:** `[FAILED] Auth Login Flow — My App`
- **Fields:** Feature, Module, Environment, Pass/Fail counts
- **Description:** List of failed test names with first error line
- **Footer:** Link to run in platform | Timestamp
- **Mention:** Optional role mention `<@&roleId>` prepended to message on failure

### Configuration

```typescript
interface DiscordConfig {
  webhookUrl: string;        // Discord incoming webhook URL
  username?: string;         // Bot display name (default: 'QA Platform')
  avatarUrl?: string;        // Bot avatar URL (optional)
  mentionRoleId?: string;    // Discord role ID to ping on failure
}
```

### Setup Instructions (shown in UI)

1. In Discord: Server Settings → Integrations → Webhooks → New Webhook
2. Select channel, copy webhook URL
3. Paste URL into the config form
4. (Optional) Copy a Role ID from Server Settings → Roles to enable pinging on failure

## GitHub Issues Plugin

### When to use
Projects already using GitHub for code hosting and issue tracking.

### Auth Strategy

Reuses the `RepoConnection` OAuth token if one exists for the same repo (from Phase 5.5 RAG), otherwise falls back to a separately entered PAT. This avoids requiring users to authenticate twice.

### Ticket Creation

`createTicket()` calls `POST /repos/{owner}/{repo}/issues`:

```typescript
{
  title: `[QA Failure] ${featureName} — ${testName}`,
  body: `
## Test Failure Report

**Feature:** ${featureName}
**Module:** ${moduleName}
**Environment:** ${environmentName}
**Run:** [View in QA Platform](${runUrl})

## Failed Step

> ${stepDescription}

**Error:** \`${errorMessage}\`

${screenshotUrl ? `## Screenshot\n![Failure screenshot](${screenshotUrl})` : ''}

---
*Generated by [QA Platform](${platformUrl}) · Run #${runId}*
  `,
  labels: config.labels,        // e.g. ['bug', 'qa-failure']
  assignees: config.assignees,  // GitHub usernames
  milestone: config.milestone,  // milestone number
}
```

### Duplicate Detection

Before creating: search open issues with title `[QA Failure] {featureName} — {testName}`. If found, add a comment to the existing issue instead of creating a duplicate.

### Configuration

```typescript
interface GitHubIssuesConfig {
  owner: string;          // GitHub org or username
  repo: string;           // repository name
  token: string;          // PAT (classic or fine-grained with Issues:write)
  labels: string[];       // labels to apply (must exist in repo)
  assignees: string[];    // GitHub usernames to assign
  milestone?: number;     // milestone number
}
```

## GitLab Issues Plugin

### When to use
Projects using GitLab for code hosting (cloud or self-hosted).

### Auth Strategy

Reuses the `RepoConnection` token if one exists for the same GitLab project, otherwise uses a separate PAT.

### Self-Hosted GitLab

The `baseUrl` config field points to the self-hosted instance (e.g. `https://gitlab.company.com`). If omitted, defaults to `https://gitlab.com`.

### Ticket Creation

`createTicket()` calls `POST /api/v4/projects/{projectId}/issues`:

```typescript
{
  title: `[QA Failure] ${featureName} — ${testName}`,
  description: markdownBody,   // same structure as GitHub plugin
  labels: config.labels.join(','),
  assignee_ids: resolvedUserIds,
  milestone_id: config.milestoneId,
  confidential: false,
}
```

### Configuration

```typescript
interface GitLabIssuesConfig {
  baseUrl?: string;          // default: https://gitlab.com
  projectId: number;         // GitLab project ID (visible in Settings → General)
  token: string;             // PAT with api scope
  labels: string[];
  assigneeUsernames: string[];
  milestoneId?: number;
}
```

## Linear Plugin

### When to use
Developer-focused teams using Linear as their issue tracker. Linear is popular as a modern, fast Jira alternative.

### Transport

Linear GraphQL API with a Personal API Key (generated in Linear → Settings → API).

### Ticket Creation

`createTicket()` uses the `issueCreate` GraphQL mutation:

```graphql
mutation CreateIssue($input: IssueCreateInput!) {
  issueCreate(input: $input) {
    success
    issue {
      id
      url
      identifier
    }
  }
}
```

Input:
```typescript
{
  teamId: config.teamId,
  title: `[QA Failure] ${featureName} — ${testName}`,
  description: markdownBody,
  priority: config.priority,   // 0=No priority, 1=Urgent, 2=High, 3=Medium, 4=Low
  labelIds: [config.labelId],
  assigneeId: config.assigneeId,
}
```

### Configuration

```typescript
interface LinearConfig {
  apiKey: string;           // Linear Personal API Key
  teamId: string;           // Linear team ID (UUID)
  labelId?: string;         // Label UUID (e.g. "QA Failure" label)
  assigneeId?: string;      // Linear user UUID
  priority: 0 | 1 | 2 | 3 | 4; // default: 2 (High)
}
```

### Setup Instructions (shown in UI)

1. In Linear: Settings → API → Personal API Keys → Create Key
2. Copy Team ID from Linear URL: `linear.app/{workspace}/team/{teamId}/...`
3. (Optional) Create a "QA Failure" label in Linear and copy its ID via API

## Google Chat Plugin

### When to use
Teams using Google Workspace (formerly G Suite) — Google Chat is their Slack equivalent.

### Message Format

Google Chat Card v2:
- **Header:** Icon + "QA Platform" + subtitle (`Run #142 failed`)
- **Section 1:** Feature, Module, Environment, Pass/Fail counts
- **Section 2:** Failed test list (up to 5 tests)
- **Button:** "View Full Report" → deep link to run

### Configuration

```typescript
interface GoogleChatConfig {
  webhookUrl: string;     // Google Chat space webhook URL
  threadKey?: string;     // Optional: post replies to a specific thread
}
```

### Setup Instructions (shown in UI)

1. In Google Chat: Open the Space → Apps → Add webhooks → Add
2. Copy the webhook URL
3. (Optional) Create a thread and use its key to keep notifications together

## ClickUp Plugin

### When to use
Teams using ClickUp as their project management tool. Common in QA-led organisations and product teams.

### Transport

ClickUp REST API v2 with a Personal API Token (generated in ClickUp → Profile → Apps).

### Ticket Creation

`createTicket()` calls `POST /api/v2/list/{listId}/task`:

```typescript
{
  name: `[QA Failure] ${featureName} — ${testName}`,
  description: markdownBody,
  priority: config.priority,   // 1=urgent, 2=high, 3=normal, 4=low
  assignees: resolvedUserIds,
  tags: config.tags,
  status: config.status,       // e.g. 'Open'
  custom_fields: [
    { id: 'environment_field_id', value: environmentName }
  ]
}
```

### Configuration

```typescript
interface ClickUpConfig {
  apiToken: string;      // Personal API Token
  listId: string;        // ClickUp List ID (from URL)
  priority: 1 | 2 | 3 | 4; // default: 2 (high)
  assignees: string[];   // ClickUp user IDs (numeric)
  tags: string[];        // ClickUp tag names
  status?: string;       // Task status name (default: first status in list)
}
```

## PagerDuty Plugin

### When to use
Teams with on-call rotations who need immediate alerting when production-critical tests fail. Especially relevant for health-check suites, smoke tests, and P0 tests run after deployments.

### Transport

PagerDuty Events API v2 (`POST https://events.pagerduty.com/v2/enqueue`). Uses an Integration Key (Routing Key), not OAuth. This can be created in PagerDuty under Services → Integrations → Add integration → Events API v2.

### Trigger on Failure

```typescript
{
  routing_key: config.integrationKey,
  event_action: 'trigger',
  dedup_key: `qa-platform-${featureId}-${environmentId}`, // prevents duplicate incidents
  payload: {
    summary: `QA Failure: ${featureName} — ${failedCount} test(s) failed`,
    severity: config.severity,   // 'critical' | 'error' | 'warning' | 'info'
    source: `QA Platform — ${projectName}`,
    component: featureName,
    group: moduleName,
    class: 'test_failure',
    custom_details: {
      feature: featureName,
      module: moduleName,
      environment: environmentName,
      failedTests: failedTestNames,
      runUrl: runUrl,
    }
  },
  links: [{ href: runUrl, text: 'View Run' }],
}
```

### Auto-Resolve on Pass

When a subsequent run of the same feature in the same environment passes, send a `resolve` event using the same `dedup_key`. This auto-resolves the PagerDuty incident without human intervention.

```typescript
{
  routing_key: config.integrationKey,
  event_action: 'resolve',
  dedup_key: `qa-platform-${featureId}-${environmentId}`,
}
```

### P0-Only Mode

When `triggerOnlyForP0: true`, PagerDuty is only triggered if at least one failed test has value tier `ESSENTIAL` or `VALUABLE` (from Phase 8 Test Value Scoring). This prevents low-value flaky tests from paging on-call engineers.

### Configuration

```typescript
interface PagerDutyConfig {
  integrationKey: string;                              // Events API v2 routing key
  severity: 'critical' | 'error' | 'warning' | 'info'; // default: 'error'
  triggerOnlyForP0: boolean;                           // default: false
  autoResolve: boolean;                                // default: true
}
```

## Failure Action Panel (Updated)

The step failure panel in the Feature Player (Phase 3-E) needs updating to show all configured bug-tracking integrations:

**Before (Phase 3-E):**
- 💬 Add Comment
- ⏭ Skip Step
- ⏭ Skip Test
- 🔄 Retry Step
- 🐛 Create Jira Ticket ← hardcoded
- 📣 Notify Slack/Teams ← hardcoded
- ⏹ Abort Run

**After (Phase 10):**
- 💬 Add Comment
- ⏭ Skip Step
- ⏭ Skip Test
- 🔄 Retry Step
- 🐛 Create Issue ▾ ← dropdown: shows all configured bug trackers (Jira / GitHub Issues / GitLab Issues / Linear / ClickUp)
- 📣 Notify ▾ ← dropdown: shows all configured notification integrations (Slack / Teams / Discord / Google Chat)
- ⏹ Abort Run

Dropdown only shows integrations that have been configured for the project. If none configured for a category, the button links to the integrations settings page.

## Adding a New Integration in the Future

To add another integration (e.g. Asana, monday.com, Basecamp):

1. Implement `IntegrationPlugin` interface in `apps/api/src/modules/integrations/plugins/`
2. Add the new type to `IntegrationType` enum and run migration
3. Register in `IntegrationPluginRegistry`
4. Add config form to the Add Integration modal (frontend)
5. Update this doc

No changes to the trigger engine, notification rules, or run flow.
